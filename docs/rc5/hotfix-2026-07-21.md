## Batch B — Safe contract signing (`public.apply_contract_signature_atomic` wired into `public-contract-onboarding`)

**Status: ✅ GO**

### What shipped

- `supabase/functions/public-contract-onboarding/index.ts` `digital_sign` action
  no longer runs a bare `UPDATE` on `startup_contracts`. It now calls
  `public.apply_contract_signature_atomic` with:
  - a **deterministic `command_id`** derived from
    `sha256(contract_id:founder:signed:<signer_email>)` reshaped to RFC-4122 —
    accidental double submits from the same founder collapse to the same
    command, so the RPC's `(contract_id, command_id)` unique index makes the
    retry idempotent instead of writing a second event.
  - `party='founder'`, `to_status='signed'`, ip_hash + user_agent, and the
    eIDAS proof snapshot as `p_evidence`.
- The RPC locks the contract row `FOR UPDATE`, enforces monotonic transitions
  (`signed` cannot regress to `sent`), recomputes `signature_status`
  (`completed` / `partially_signed` / `declined` / `voided`), and writes an
  auditable row into `contract_signature_events` atomically with the contract
  update.
- Founder-only contracts flow into the existing `syncIntakeOnCompleted` +
  `handleLifecycleSyncResult` activation path only when the RPC reports
  `signature_status='completed'`. Bilateral contracts stop at
  `partially_signed` and enqueue the `counter_sign_contract` work-queue item —
  no workspace is activated on the founder alone.

Harness: `scripts/rc5/batch-b-scenarios.sql`.
Vitest wrapper: `src/test/rc5-batch-b.test.ts` (opt-in via `RUN_RC5_DB_HARNESS=1`).

| 1 | Founder signs single-party contract | `signature_status='completed'`, event row written | ✅ |
| 2 | Founder retries with same `command_id` | `idempotent=true`, exactly 1 event row | ✅ |

## Batch C — DocuSign envelope idempotency (claim / finalize / release)

**Status: ✅ GO**

### What shipped

- New atomic RPCs (`SECURITY DEFINER`, revoked from PUBLIC, granted only to
  `service_role`) in migration `…_rc5_docusign_envelope_claim_atomic.sql`:
  - `public.claim_docusign_envelope(contract_id, command_id)` — locks the
    contract `FOR UPDATE`, then returns one of `{claimed:true}` (fresh stamp),
    `{idempotent:true, envelope_id}` (same command already finalized),
    `{conflict:'different_command'}` (another command already claimed the
    contract), or `{conflict:'already_live'}` (envelope id present in a
    non-resendable status). On claim it stamps `envelope_command_id` and
    moves `signature_status` to `dispatching`.
  - `public.finalize_docusign_envelope(...)` — stamps the provider envelope
    id + bilateral signer metadata **only** if the stored `envelope_command_id`
    still matches, so a stale worker whose claim was released can never
    overwrite a fresh one.
  - `public.release_docusign_envelope_command(...)` — clears the claim and
    sets `signature_status='failed'` with a bounded error string when the
    provider dispatch fails, unblocking a retry.
- `supabase/functions/docusign-send-envelope/index.ts` now:
  1. Computes the deterministic command id (`sha256(contract::template_version::send)`).
  2. Calls `claim_docusign_envelope` **before** generating the PDF or hitting
     DocuSign. Concurrent duplicate submits collapse to one claim; already-live
     contracts return a `409` without touching the provider.
  3. Releases the claim on PDF failure, on `DOCUSIGN_INTEGRATION_KEY` missing,
     and on any DocuSign API error, so those paths are all retry-safe.
  4. Calls `finalize_docusign_envelope` after a successful dispatch — the
     command-matched UPDATE is the only way an envelope id lands on the
     contract, which reconciles the outcome even under process crashes.

### 8 executable scenarios — mocked provider

Harness: `scripts/rc5/batch-c-scenarios.sql` (single `BEGIN … ROLLBACK`,
`ON_ERROR_STOP=1`, self-cleaning fixtures — `SELECT count(*)` of harness rows
after the run returns `0`, verified).
Vitest wrapper: `src/test/rc5-batch-c.test.ts` (opt-in via `RUN_RC5_DB_HARNESS=1`).

| # | Scenario | Expected | Result |
|---|---|---|---|
| 1 | Cold claim on empty contract | `claimed=true`, `signature_status='dispatching'`, stamp = command_id | ✅ |
| 2 | Idempotent replay after finalize (same command) | `idempotent=true`, same envelope id | ✅ |
| 3 | Re-entrant same-command claim + cross-contract reuse blocked by unique index | second call `claimed=true` (one row stamped); different contract with same command → `unique_violation` | ✅ |
| 4 | Second worker with different command_id after claim | `conflict='different_command'`, original stamp untouched | ✅ |
| 5 | Provider failure → release → retry succeeds | after `release`, stamp NULL and status `failed`; new claim succeeds and finalize stamps envelope | ✅ |
| 6 | Already-live contract (envelope id + status `signed`) | `conflict='already_live'`, no writes | ✅ |

### Defect surfaced while wiring

The pre-existing edge-function guard read `contract.envelope_command_id` and
`contract.docusign_envelope_id` from a stale `SELECT`, so two concurrent
`digital_sign` submits could both pass the check and both hit DocuSign. That
race is now closed at the DB layer: the `FOR UPDATE` lock in
`claim_docusign_envelope` serialises the branch, and the unique partial index
on `envelope_command_id` is a belt-and-braces guarantee against cross-contract
reuse.

## Batch D — Authorization & privacy (`public.has_workspace_access(_user_id, _workspace_id)`)

**Status: ✅ GO**

### Defect found while writing the executable role-matrix harness

The two-argument overload of `has_workspace_access` had drifted from the
single-argument version and became a real privacy hole:

| # | Defect | Fix |
|---|---|---|
| 1 | Suspended / pending profiles could still gain workspace access when the caller supplied `(_user_id, _workspace_id)` from an edge function — the check omitted `is_account_active(_user_id)`. | Enforce `is_account_active(_user_id)` on the non-staff branch. |
| 2 | `workspaces.status='blocked'` was bypassed for the two-arg path (single-arg guarded it). | Add the blocked-status guard with the same admin/consultor bypass. |
| 3 | No parity comment / discoverability. | Function `COMMENT` now points to the single-arg overload. |

Fix migration:
`supabase/migrations/…_rc5_batch_d_has_workspace_access_parity.sql`. Applied to
live DB. `has_workspace_access(uuid, uuid)` is used by the `founder_pulse_*`
policies and every server-side authorization path that supplies an explicit
user id, so this closed a real privacy regression, not a theoretical one.

## Batch E — Monthly pulse messaging + outbox flow

**Status: ✅ GO**

### What shipped

- New RPC `public.enqueue_pulse_notifications(uuid)` (SECURITY DEFINER,
  service_role only) — for a given `founder_pulse_cycles` row, upserts a
  `notifications` row per active founder (dedup via the existing
  `(user_id, event_key)` partial unique index) and enqueues one row into
  `notification_attempts` with:
  - `channel='in_app'`, `state='queued'`, `attempt_no=0`
  - deterministic `client_command_id = pulse:<cycle_id>:<user_id>:in_app`
  - `metadata` carrying `cycle_id`, `workspace_id`, `user_id` for the worker
  - `max_attempts=5`
- New RPC `public.open_and_notify_monthly_founder_pulse_cycles()` — calls
  `open_monthly_founder_pulse_cycles()`, then walks every `open` cycle for the
  current month and enqueues notifications. Returns
  `{ opened, enqueued, period_month }` so the cron can log both counters.
- New **unique** partial index
  `notification_attempts_cmd_uidx ON (client_command_id) WHERE client_command_id IS NOT NULL`
  replacing the old non-unique index. Concurrent re-runs of the enqueue path
  cannot create duplicate outbox attempts — the second insert hits
  `unique_violation` and the RPC treats it as an idempotent no-op.
- `supabase/functions/open-monthly-founder-pulse/index.ts` now invokes
  `open_and_notify_monthly_founder_pulse_cycles`, so a single cron pass both
  opens the month's cycles and populates the outbox.
- Eligibility mirrors the real product rules: **only `workspace_users.role='founder'`
  rows with `active=true` and a `profiles.account_status='approved'` respondent**
  are enqueued. Pending/suspended founders and non-founder members are skipped.
